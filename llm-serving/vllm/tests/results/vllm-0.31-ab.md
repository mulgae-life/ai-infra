## 성능 (`speed_test.py` 3회, 동시성 1·5·10 × max_tokens 512·2048)
통과 조건: 처리량·디코딩 TPS 새/옛 ≥ 0.95, TTFT 새/옛 ≤ 1.05 (3회 중앙값). 경계 구간(0.93~0.97, 1.03~1.07)이면 2회 더 재서 5회 중앙값.
- 표의 TTFT는 회차별 p50, TPS는 회차별 요청당 디코딩 속도 p50이다(그 3개 값의 중앙값). `speed_test`의 TPOT는 이 디코딩 TPS 중앙값의 역수라 따로 적지 않는다.
- **TTFT p95는 이 시험으로 판정하지 않는다.** `speed_test`는 p95를 계산만 하고 저장하지 않으며(`speed_test.py:289,467`), 동시성 1은 표본이 5건이라 p95가 의미 없다. p95는 `traffic_test` 스트리밍 3회(요청 60·동시 10, 아래 "품질·회귀 집중" 절)로 판정한다.
- 서버 처리량(`svrTPS`, 회차 원본 `speed_r1~3.txt`) 3회 중앙값의 새/옛: gemma31b 1.072~1.097, gemma26b 1.158~1.258, qwen-mtp-off 1.114~1.341. 6개 시나리오 모두 기준(≥ 0.95) 이상이다. gemma31b·gemma26b는 5회 판정으로 바뀐다(아래 각 변형 판정 문단).
- **회차 변동 칸 (⏳)과 처리 원칙** (10-09, 4·5회차 결과를 보기 전에 고정. 코덱스 2라운드 D1 권고 수용)
  - 판정 기준은 그대로 중앙값이다. 3회 관측 범위 안에서 판정이 뒤집힐 수 있는 칸을 추가 측정 대상으로 골랐다. 고를 때 쓴 비관 비율은 지연이면 새 최댓값/옛 최솟값, 처리량·속도면 새 최솟값/옛 최댓값이다. 이 값은 관측 범위일 뿐 신뢰구간이 아니며 새 실패 기준으로 쓰지 않는다.
  - 대상 칸은 TTFT 기준 gemma31b 5×512(1.21)·10×2048(1.34), gemma26b 5×512(1.78)이다. 두 변형은 옛·새 모두 4·5회차를 같은 호출로 추가한다(A/B 2차분). 4·5회차는 1~3회차와 다른 기동 회차이고 회귀 탐침·트래픽 시험 뒤에 재므로 예열·캐시 상태가 같다고 가정하지 않는다.
  - 판정은 5회 중앙값으로 한다. 1~3회차 묶음과 4·5회차 묶음을 나란히 적어 묶음 전체가 옮겨 갔는지 본다. 5회 중앙값이 경계 구간에 있거나 판정을 뒤집는 변동이 남으면 그 칸은 보류한다. 관측 범위 전체가 통과 쪽이면 변동 폭만으로는 보류하지 않는다.
  - 이 원칙은 양방향이다(코덱스 4라운드 Q4). 중앙값이 실패여도 관측 범위가 기준 안쪽까지 걸치면 보류이고, 관측 범위 전체가 실패 쪽일 때만 실패로 적는다. 서버 처리량(svrTPS)은 계획서 판정 기준의 "처리량"이므로 TTFT·디코딩 속도와 같은 규칙으로 판정한다(4라운드 H2).
  - 판정 전에 자료 유효성을 본다(4라운드 Q3). 예정 시나리오 6개마다 옛·새 모두 1~5회차가 있고 회차마다 요청이 전부 성공(`ok=N/N`, 429·err 0)해야 판정한다. 회차가 빠지면 임시 계산이고, 옛 쪽 요청 실패는 기준선 무효(보류), 새 쪽 요청 실패는 시험 실패다. 대조 도구는 스크래치 `speed_compare.py`(반례 모의 11종)다.

### 새 버전 안의 `fp8` ↔ `fp8_per_tensor` (계획 P3 FP8 항목, 1회)
0.31 소스에서 온더플라이 `fp8`은 deprecated 경고를 낸 뒤 `fp8_per_tensor` 설정으로 바꿔 처리한다(`model_loader/weight_utils.py:341-348`, 약칭 정의 `config/quantization.py:188-191`: 선형·MoE 가중치 모두 정적 텐서 단위 FP8). 실제 기동으로는 MoE 층까지 덮는 gemma26b를 `quantization: fp8_per_tensor`로 바꾼 묶음(시험장 `bundle/gemma26b-pt`, 이 한 줄만 다름)으로 확인한다. 비교 대상은 같은 0.31의 gemma26b(`fp8`)이며 기동 로그의 선형·MoE 방식 줄과 회귀 탐침 결과·greedy 일치를 본다.

### 판정 요지
- 운영 모델인 Gemma 31B는 시험한 기능·품질 판정 항목에서 회귀가 관측되지 않았다. 디코딩은 8~10% 빨라졌고, 2시간 부하에서 요청 실패가 없었다. 성능은 ❌ 없이 5칸이 보류다.
- **운영 Gemma 31B는 MTP를 끈다(결정 ⑨).** 지금 운영 조합(옛 nightly + KV auto + MTP 켬)은 추론 켬 요청의 JSON 스키마·도구 호출 강제가 108/320 깨졌고, MTP만 끄면 0/320이다. 0.31은 켬·끔 모두 0이지만 요청 혼합 오염(#46088)이 미수정이고 우리 축소 재현은 검출력이 확인되지 않았다. 위 기능·장시간 부하는 MTP 켬 기준이라, 0.31 + MTP 끔 조합을 10-09 저녁 pip 환경에서 따로 시험했다. 기능 31/31, 회귀 통과, 게이트웨이 호환 통과, 2시간 부하 2,938건 실패 0이다(아래 "MTP 끔 운영 조합 점검"). 처리량은 MTP 켬의 약 37%다.
- **게이트웨이는 반드시 함께 반영한다.** 옛 게이트웨이와 0.31 Qwen 조합에서는 18건 중 4건이 기대와 달리 사고를 켰다(14건 통과). 생략+최상위 effort, 생략+템플릿 effort의 스트리밍·비스트리밍 네 사례다. 운영 반영 순서는 새 게이트웨이를 먼저 옛 vLLM 위에 올리는 것이다(part3 P4 0단계).

### 측정 조건의 제한
- **외부 점유**: gemma31b 마지막 약 35분과 qwen-mtp-off 전체는 GPU2의 외부 점유(2,951 MiB)와 함께 측정했다.
  - 관찰 시점마다 사용률이 0%였지만, 이것이 전 구간에 간섭이 없었다는 것을 입증하지는 않는다.
  - 메모리 기록의 GPU 값은 장치 총량이다. vLLM 단독의 GPU 메모리 추세와 외부 부하가 성능에 준 영향은 분리하지 않았다.
  - 장시간 부하 결과는 성능 판정에 쓰지 않는다.
- **연쇄 스크립트의 자동 판정 한계**(코덱스 R1-03·R1-04, 2판부터 있던 경로)
  - 자동 "통과 후보"는 로그를 읽지 못한 경우와 오류가 0건인 경우를 구분하지 못한다.
  - 런처 조회가 실패하면 런처가 없는 것으로 처리한다.
  - 실행 중인 연쇄는 고치지 않았다. 이 결함은 그대로 남는다. 연쇄를 다시 쓰려면 두 경로를 먼저 고치고 검증해야 한다.
  - 예외: 10-09 저녁 MTP 끔 운영 조합 점검은 두 경로를 고치지 않은 4판을 재사용했다. 그 실행의 수동 판정 관문은 위 "MTP 끔 운영 조합 점검" 절에 있다. 다음 재사용 전에는 두 경로를 고친다.
  - 이번 실행은 사람이 원문을 직접 확인해 보완했다. 세 변형(qwen-mtp-on, gemma31b, qwen-mtp-off) 모두 엔진·게이트웨이 로그를 확인했다. qwen-mtp-off는 종료 뒤 프로세스 잔존도 PID·세션 번호로 확인했다(결과 `collab/final-verdict-review/qwen_off_post/`).
  - qwen-mtp-on과 gemma31b의 원문 독립 검사(10-09 12시, `scratchpad/soak_log_audit.sh`, 결과 `collab/final-verdict-review/log_audit_r3.txt`)
    - 읽기 확인: 엔진·게이트웨이 로그 네 개 모두 크기, 줄 수, md5를 남겼다. 검사는 awk 종료 0, grep 종료 1(정상 무일치)로 끝났다. 엔진 로그는 종료 요청 줄까지 이어진다.
    - 검사 구간: 연쇄의 "기준 줄" 다음부터 첫 `[shutdown]` 줄 앞까지다(qwen-mtp-on 223~6,919줄, gemma31b 184~12,132줄). 검색식은 연쇄와 같은 `ERROR|Traceback|EngineDeadError|EngineCore.*died|out of memory|OutOfMemory`이고 대소문자를 구분한다. 이 구간에서 오류 줄과 자동 재기동은 둘 다 0이다.
    - 기동 단계의 일치 줄(qwen 18·45줄, gemma 20·48줄)은 deep_ep 가져오기 경고다.
    - 종료 요청 뒤: qwen-mtp-on은 오류 줄 0이다. gemma31b는 8줄(`EngineDeadError` 1건)이다. 이 오류는 abort 종료(대기 0초)에서 EngineCore를 SIGTERM 뒤 강제로 끝낸 직후 출력 처리기가 낸 것으로, 문맥상 종료 경로에서 나왔다.
    - 게이트웨이 로그(0.8 MB·1.8 MB): `Traceback|ERROR`와 대소문자 무시 `error|traceback` 모두 0줄이다.
