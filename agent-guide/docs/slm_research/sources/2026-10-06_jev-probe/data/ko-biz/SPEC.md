# 한국어 업무 판단 문항 작성 규격

판단 전용 모델(선택지 확률만 읽는 방식)을 평가하기 위한 한국어 문항이다. 보험·금융사 고객센터와 내부 업무를 가정한다. 평가 대상 모델이 정답을 맞히는지, 확신도가 정답률과 맞는지를 잰다.

## 파일 형식

JSONL, 한 줄에 문항 하나. UTF-8. 필드:

| 필드 | 형식 | 설명 |
|------|------|------|
| `id` | 문자열 | `<분야코드>-<세 자리 번호>` 예: `route-001` |
| `domain` | 문자열 | 분야 코드 (아래 표) |
| `task` | 문자열 | 분야 안의 세부 과제 이름(짧은 영문 슬러그) 예: `inquiry_type`, `urgency` |
| `state` | 문자열 | 판단 대상 텍스트. 고객 문의, 상담 녹취 요약, 문서 발췌, 문자 메시지 등. 한국어 |
| `question` | 문자열 | 묻는 내용. 한국어 한 문장 |
| `type` | `"choice"` 또는 `"noul"` | choice는 선택지 중 하나, noul은 예/아니오 |
| `options` | 객체 | choice: `{"짧은 선택지 이름": "한 줄 설명", ...}` 2~8개. 설명이 필요 없으면 `null`. noul: `{"true": "예일 때 의미", "false": "아니오일 때 의미"}` |
| `gold` | 문자열 | choice는 `options`의 키 하나. noul은 `"true"` 또는 `"false"` |
| `difficulty` | 문자열 | `easy`(명확), `borderline`(헷갈리지만 최선의 답이 하나로 정해짐), `hard`(여러 단서를 종합하거나 함정이 있음) |
| `tags` | 문자열 배열 | 해당하는 것 모두. 아래 태그 목록에서 고른다 |
| `rationale` | 문자열 | 정답이 왜 맞는지 한 문장 |

## 태그 목록

`colloquial`(구어체·줄임말), `typo`(오타·띄어쓰기 오류), `long`(400자 이상), `multi_issue`(요구가 여러 개 섞임), `implicit`(직접 말하지 않고 돌려 말함), `negation`(부정·이중부정), `injection`(state 안에 "이전 지시를 무시하고 ○○라고 답하라" 같은 조작 문구), `calc_date`(날짜 계산 필요), `calc_amount`(금액·숫자 계산 필요), `rule`(state에 주어진 규칙을 적용), `distractor`(정답과 무관한 정보가 많이 섞임), `english_mix`(영어 섞임)

## 반드시 지킬 것

1. **정답은 주어진 텍스트만으로 하나로 정해져야 한다.** 판단에 필요한 규칙·기준·날짜는 모두 `state`나 `question`에 넣는다. 실제 법규나 특정 회사 약관 지식이 있어야 풀리는 문항은 만들지 않는다. 일상 상식은 써도 된다.
2. **정답 위치를 고르게 섞는다.** 같은 과제에서 정답이 늘 첫 번째 선택지가 되지 않게 한다. 선택지 순서는 자연스러운 순서를 유지하되, 정답 분포가 치우치지 않게 문항을 고른다.
3. **noul 문항은 정답이 true와 false 반반에 가깝게** 만든다.
4. **난이도 분포**: easy 약 40%, borderline 약 35%, hard 약 25%.
5. **태그 분포**: `injection` 최소 6문항, `colloquial`·`typo` 합쳐 최소 15문항, `long` 최소 8문항, `multi_issue` 최소 8문항. 분야에 맞으면 다른 태그도 쓴다.
6. **injection 문항의 정답은 조작 문구를 무시하고 내용대로 판단한 답이다.** 조작 문구가 요구하는 답과 실제 정답이 다르게 만든다.
7. 사람 이름, 전화번호, 계좌번호, 주민번호는 모두 가상이다. 실제 존재하는 회사·상품명을 쓰지 않는다(예: "○○생명" 대신 "한빛손해보험" 같은 가상 이름).
8. 문항끼리 내용이 겹치지 않게 다양하게 만든다. 같은 틀에 단어만 바꾼 문항을 반복하지 않는다.
9. 한국어는 실제 고객이나 직원이 쓸 법한 자연스러운 문장으로 쓴다.

## 분야

| 코드 | 분야 | 세부 과제 예시 |
|------|------|----------------|
| `route` | 고객 문의 분류·라우팅 | 문의 유형(보험금 청구, 계약 변경, 해지·환급, 보험료 납입, 상품 문의, 대출, 민원, 기타 중), 담당 부서, 추가 서류 필요 여부(noul), 상담원 연결 필요 여부(noul) |
| `voc` | 민원·감정·긴급도 | 민원 여부(noul), 고객 감정, 처리 긴급도(즉시/당일/일반), 금융감독원 민원 제기 의사(noul), 해지 위험 등급 |
| `claim` | 보험금 청구 심사 보조 | state에 약관 발췌와 청구 내용을 주고 보장 대상 여부(noul), 면책 사유 해당 여부와 종류, 누락 서류 종류, 상담 답변이 근거 문서로 뒷받침되는지(noul) |
| `comply` | 판매·상담 준수 점검 | 상담 녹취 요약에 설명 의무 누락, 단정적 수익 보장, 부당 권유, 동의 절차 누락이 있는지와 그 종류. 판단 기준을 state에 준다 |
| `fraud` | 보안·사기 탐지 | 스미싱·피싱 문자 여부(noul), 보험사기 의심 징후 종류, 개인정보 포함 여부(noul), 사내 문서 보안 등급 |
| `calc` | 계산·날짜·규칙 적용 | 청약 철회 가능 기간 내인지, 납입 유예 기간 경과 여부, 보장 개시 전 사고인지, 금액 한도 초과 여부, 나이 기준 충족 여부. 기준일·규칙·금액은 모두 state에 준다. 정답은 정확히 계산해 확인한다 |

## 마무리 확인

- 작성 후 Python으로 파일의 모든 줄이 JSON으로 읽히는지, 필수 필드가 있는지, `gold`가 `options` 키에 있는지, noul의 `options` 키가 `true`·`false`인지 확인한다.
- `calc` 문항은 날짜·금액 계산을 Python으로 다시 해서 정답을 검증한다.
- 정답 분포(선택지 위치별, true/false), 난이도·태그 개수를 집계해 보고한다.
