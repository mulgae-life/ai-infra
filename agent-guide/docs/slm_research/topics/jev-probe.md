# Jev 방식 판단 실측 — 서빙 중인 Qwen3.8-27B를 Jev 1.13과 맞대기

> 실측일: 2026-10-06 | 대상: Qwen3.8-27B-FP8 (연구계 서빙과 같은 가중치) | 비교 기준: Jev 1.13 (`jev-1.13.0`)
> 모델을 고치지 않고 선택지 확률만 읽는 방식(확률 읽기)으로 Jev와 같은 문항을 풀려 정확도, 확신도 보정, 지연, 처리량을 쟀다. 확률 읽기의 원리와 Jev 자체 조사는 [jev.md](jev.md), 원본 자료와 스크립트는 [sources/2026-10-06_jev-probe/](../sources/2026-10-06_jev-probe/README.md)에 있다.

---

## 📌 TL;DR

1. **정확도는 Jev와 같은 수준이다.** 한국어 공개 벤치(한국어 지문·한국어 지시)에서 0.837 대 0.840으로 차이가 없다. 프롬프트 조정에 쓰이지 않은 영어 판단 벤치 14종 평균은 0.806 대 0.782로 Qwen이 2.4%p 높다. 범위가 넓은 Decision Index에서는 Jev가 2~4점 앞서는데, 차이가 전문 지식·다단계 추론 벤치에 몰려 있다.
2. **확신도 보정은 Jev가 낫다.** 한국어 공개 벤치의 보정 오차(ECE)가 0.069 대 0.028이다. 온도 맞춤 한 번으로 상당 부분 메워진다. 업무 문항에서 게이트웨이 경로의 보정 오차가 0.038에서 0.016으로 줄었다.
3. **업무 판단은 분류에 강하고 계산에 약하다.** 직접 만든 한국어 업무 문항 596개에서 확률 읽기는 89.3%를 맞혔다. 날짜·금액 계산이 든 분야만 63%다. 사고 켬으로 풀면 99.5%가 되지만 문항당 수 초가 걸린다.
4. **확신도가 낮은 문항만 사고 켬으로 넘기는 2단계 구성이 실용적이다.** 확신도 0.9 미만인 23%만 넘기면 정확도가 97.8%가 되고, 문항당 평균 지연은 2.3초(중앙값 0.21초)다.
5. **단건 지연은 Jev보다 짧다.** 게이트웨이 경로 중앙값 188ms, 실험 엔진(GPU 한 장) 166ms다. Jev는 한국어 벤치에서 221ms였다(네트워크 포함).
6. **처리량은 Jev에 크게 못 미친다.** 게이트웨이 경로는 동시성 4부터 초당 6.5건에서 막힌다. Jev는 계정당 초당 80요청까지 허용한다. 같은 모델을 GPU 한 장에 올린 실험 엔진이 토큰당 약 3.5배 빨랐다. 서버의 GPU끼리 직접 통신(P2P)이 안 돼 두 장 분할(TP2)의 통신이 호스트 메모리를 거치는 것이 가장 유력한 원인이다.
7. **프롬프트가 정확도를 크게 움직인다.** 우리 쪽 시스템 프롬프트를 빼면 5.4%p 떨어졌고, 선택지 순서를 돌리면 선택지형 문항의 16%에서 답이 바뀌었다.

## 1. 실험 설계

### 1.1 묻는 것

1. 서빙 중인 Qwen3.8-27B-FP8에 확률 읽기를 적용하면 Jev 1.13과 비교해 정확도와 확신도 보정이 어느 수준인가
2. 한국어 업무 판단에 쓸 수 있는가, 쓴다면 어떤 프롬프트와 구성이 맞는가
3. 우리 GPU(L40S)에서 지연과 처리량이 Jev와 비교해 어느 수준인가

### 1.2 구성

```
  [실험 엔진]  GPU 3, L40S 1장 (TP1)              [게이트웨이 경로]  GPU 0·1, L40S 2장 (TP2)
   simple-jev 프롬프트 컴파일러                     클라이언트 → :5015 게이트웨이 → :7080 vLLM
   + vLLM AsyncLLM, logprob_token_ids              정체성 안내문이 시스템 프롬프트에 붙음
   Jev와 같은 요청 형식 (/v1/classifier)            우리가 쓴 짧은 프롬프트, 상위 20개 점수
   선택지 점수를 빠짐없이 정확히 읽음                 사고 끔(확률 읽기·짧은 생성), 사고 켬
              │                                              │
              └─────── 같은 가중치: Qwen3.8-27B-FP8 ─────────┘
                                   │
                  Jev 1.13 공개 결과·문항별 원응답과 비교
```

- **실험 엔진**은 공개 재현 서버 simple-jev의 프롬프트 생성과 응답 조립을 그대로 쓰고, 모델 계산만 vLLM으로 바꾼 서버다. 프롬프트 정책은 simple-jev가 Qwen3.8-27B에 자동으로 고르는 `shared_examples_binary`다. 서빙 인스턴스에 부하를 주지 않으려고 비어 있던 GPU 3에 따로 띄웠다.
- **게이트웨이 경로**는 지금 연구계 클라이언트가 쓰는 길 그대로다. `max_tokens: 1`, `logprobs`, `top_logprobs: 20`, 사고 끔을 붙여 보낸다. 선택지 앞에 A, B, C를 붙인 짧은 한국어 프롬프트를 직접 썼다(5.5절).
- **vLLM 직접(:7080)**은 게이트웨이를 건너뛴 비교군이다. 정체성 안내문이 붙지 않는다.

실험 엔진을 검증하려고 simple-jev가 공개한 개발용 묶음 477문항을 먼저 풀렸다. 446문항을 맞혀, simple-jev가 같은 모델의 bf16 원본으로 공개한 445문항과 거의 같았다. FP8 체크포인트와 vLLM 계산으로 바꿔도 결과가 유지된다.

|------|:---:|------|------|

### 1.4 한국어 업무 문항

보험·금융사 고객센터와 내부 업무를 가정해 6개 분야 100문항씩 만들었다. 분야는 고객 문의 분류(route), 민원·감정·긴급도(voc), 보험금 청구 심사(claim), 판매·상담 준수 점검(comply), 보안·사기 탐지(fraud), 계산·날짜·규칙 적용(calc)이다. 선택지형(choice) 366문항과 예/아니오형(noul) 230문항이다.

난이도는 쉬움 40%, 경계 35%, 어려움 25%로 나눴다. 구어체, 오타, 긴 지문, 요구 여러 개, 돌려 말하기, 부정문, 조작 문구 삽입("이전 지시를 무시하고 ○○라고 답하라"), 날짜·금액 계산, 규칙 적용, 방해 정보, 영어 섞임 같은 태그를 붙였다. 판단에 필요한 규칙과 날짜는 모두 지문 안에 넣어, 실제 법규나 약관 지식 없이 답이 하나로 정해지게 했다. 인물·회사·번호는 모두 가상이다. 작성 규격은 원본 폴더의 `SPEC.md`다.

정답을 가린 채 별도 검수를 거쳤다. 600문항 모두 검수자 답이 정답과 같았고, 검수자가 정답이 둘로 읽힐 여지가 있다고 이의를 단 4문항을 뺐다. **작성과 검수를 모두 같은 계열 모델(Claude)이 했다**는 한계가 있다. 실제 업무 데이터가 아니고, 사람이 매긴 정답도 아니다.

## 4. 정확도 — Decision Index 0.2.1 표본

Decision Index는 판단 전용 모델 순위표다. 0.2.1판은 38개 벤치를 지식, 언어, 검색, 도구, 예술 5개 영역으로 나눠, 우연 수준을 뺀 점수(skill)를 영역별로 가중 평균한다. 실험 엔진으로 벤치마다 약 40요청씩 1,480요청을 순위표와 같은 방식(한 번에 하나씩, 실험 엔진의 `/v1/systemone`)으로 풀렸다.

공식 채점기는 전체 문항을 분모로 잡아 표본에 없는 문항을 미응답으로 센다. 그래서 표본 행만 담은 채점용 묶음을 따로 만들어 공식 채점 코드로 다시 채점했다. HLE는 문항 접근 승인이 필요해 표본에 없으므로, Jev와 simple-jev도 순위표의 벤치별 값을 같은 공식으로 HLE 없이 다시 합산했다. HLE를 넣은 합산이 공개 지수(Jev 57.91, simple-jev 55.74)와 정확히 같아, 합산 방식은 검증됐다.

| 영역 | Qwen3.8 FP8 (표본) | simple-jev Qwen3.8 bf16 (전체) | Jev 1.13 (전체) |
|------|:---:|:---:|:---:|
| 지식 (GPQA, MMLU-Pro, BBH 등 9종) | 40.6 | 41.1 | **57.2** |
| 언어 (ContractNLI, ANLI, RAGTruth 등 10종) | 62.0 | 62.1 | 62.0 |
| 검색 (BANKING77, BRIGHT, PhishNChips 등 6종) | 56.8 | 63.3 | 55.4 |
| 도구 (BFCL, ToolRet, When2Call 등 5종) | 77.2 | 76.2 | 75.1 |
| 예술 (유머, 음악, 색 이름 등 7종) | 32.4 | 36.5 | 37.7 |
| **지수 (HLE 제외)** | **55.5** | **57.2** | **59.5** |

- **Jev가 지수로 2~4점 앞선다.** 차이는 거의 다 지식 영역에서 난다. GPQA Diamond(0.45 대 0.79), MMLU-Pro(0.60 대 0.83), BBH(0.70 대 0.93)처럼 전문 지식과 다단계 추론이 필요한 벤치에서 Jev가 20~30%p 높다.

- **우리 표본은 simple-jev 공개값보다 1.7점 낮다.** 벤치별 skill 차이의 평균이 −1.9점(표준오차 1.1)이다. 벤치당 40요청이라 벤치별 표본 오차가 크고(차이의 표준편차 6.9점), BRIGHT는 긴 입력 1건이 실험 엔진의 최대 길이(32,768토큰)를 넘어 빠졌다. FP8과 vLLM으로 바꾼 영향은 이 오차 안에 있다.

### 6.3 입력 길이와 질문 묶음

게이트웨이 경로, 동시성 1. 처음 보는 문서(캐시 없음)와, 같은 문서에 질문만 바꿔 다시 물은 경우(캐시 있음)를 비교했다.

| 8,000자 | 약 4,300 | 1,935ms | 494ms |

|:---:|:---:|:---:|:---:|
| 1 | 532ms | 580ms | 577ms |
| 4 | 1,030ms | 2,321ms | 2,316ms |
| 8 | 1,826ms | 4,819ms | 4,875ms |
| 16 | 6,378ms | 9,970ms | 9,893ms |

- **질문 수에 거의 비례해 늘어난다.** 질문마다 문서 부분을 다시 계산하기 때문이다. Jev는 질문 13개를 한 요청에 묶으면 따로 보낼 때보다 10배 빠르다고 밝혔다. 우리 쪽은 질문을 하나씩 보낼 때(질문당 약 0.58초)보다 묶어도 1.5~2.5배 빨라지는 데 그친다.
- **첫 질문으로 문서를 캐시에 올려도 효과가 없다.** 2,000자 문서는 약 1,300토큰이라 784토큰 단위로 한 칸만 캐시되고, 나머지는 질문마다 다시 계산된다. 위 길이별 표처럼 문서가 4,000토큰을 넘으면 캐시가 크게 듣는다.

### 6.4 서빙 인스턴스가 느린 이유

| 확인한 것 | 결과 | 뜻 |
|------|------|------|
| :7080에 토큰을 직접 넣은 요청과 채팅 요청 비교 (동시성 16) | 9.29 대 9.32건/s | API 서버의 템플릿·토큰화·멀티모달 전처리는 병목이 아니다 |
| 상위 20개 점수 반환 유무 | 9.32 대 9.39건/s | 점수 반환 비용도 아니다 |
| 엔진 로그 (동시성 16 실행 중) | 프롬프트 처리량이 초당 약 2,000~2,500토큰에 머문다. 캐시 적중 0% | 엔진 계산 자체가 느리다 |
| `nvidia-smi topo -p2p r` | 모든 GPU 쌍이 `NS`(지원 안 함) | GPU끼리 직접 통신하지 못한다 |
| vLLM 기동 로그 | "Custom allreduce is disabled because your platform lacks GPU P2P capability" | 두 장 분할(TP2)의 층마다 합치기 통신이 NCCL로 호스트 메모리를 거친다 |
| 같은 L40S 한 장(TP1) 실험 엔진 | 토큰당 약 3.5배 빠름 | 통신이 없는 구성은 빠르다 |

가장 유력한 원인은 P2P 없는 TP2다. 프리필은 층마다 토큰 수에 비례하는 크기의 합치기 통신을 두 번씩 하는데, 이것이 호스트 메모리를 거치며 계산보다 오래 걸린다. 단, 실험 엔진은 MTP 추측 디코딩과 멀티모달 기능을 끈 구성이라 TP 하나만 다른 비교는 아니다. 확정하려면 서빙과 같은 설정에서 TP만 1로 바꾼 A/B가 필요하다.

## 7. 결론

### 7.1 판단

- **한국어 업무 판단에 쓸 수 있다.** 공개 벤치 정확도가 Jev와 같은 수준이고, 업무 문항의 분류형 판단도 97~99%다. 폐쇄망 운영계에서 Jev를 못 쓰는 상황의 대안이 된다.
- **계산이 든 판단은 확률 읽기에 맡기지 않는다.** 날짜·금액은 코드로 계산해 결과를 지문에 넣거나, 사고 켬으로 넘긴다.
- **확신도는 온도 맞춤을 거쳐 쓴다.** 운영과 같은 경로와 프롬프트로 맞춘다. 온도는 경로마다 달랐다(1.14~1.48).
- **처리량이 필요하면 서빙 구성부터 본다.** 지금 구성은 초당 6~9건에서 막힌다. 대량 일괄 처리에는 모자란다.

### 7.2 권장 구성

```
  요청 ─→ 확률 읽기 (게이트웨이, 사고 끔, max_tokens 1, top_logprobs 20)
            │  시스템 프롬프트: "주어진 자료만 근거로 판단하는 분류기 … 선택지 기호 하나만"
            │  선택지는 A, B, C … 20개 이하, 계산 결과는 미리 지문에 넣음
            ▼
        온도 맞춘 확신도 ≥ 기준? ──예──→ 자동 처리 (업무 문항 기준 약 75%)
            │아니오
            ▼
        사고 켬으로 다시 묻기 ──→ 그래도 애매하면 사람 검토
```

### 7.3 남은 일

| 할 일 | 이유 |
|------|------|
| TP1 A/B: 서빙과 같은 설정에서 TP만 1로 바꾼 인스턴스로 처리량 비교 | 6.4절의 원인 확정. 맞으면 TP1 두 개를 게이트웨이 뒤에 두는 구성이 처리량을 크게 늘릴 수 있다. 서빙 설정 변경이라 대표님 결정 사항이다 |
| 업무 문항을 Jev API로 풀기 | 업무 문항에는 Jev 비교가 없다. OpenRouter 키가 필요하고 문항이 외부로 나간다(가상 데이터, 비용 약 $0.02). 대표님 확인 후 |
| 실제 업무 데이터로 재검증 | 업무 문항은 같은 계열 모델이 만들고 검수했다 |
| 소형 한국어 4B 모델 비교 | jev.md 7장 후보 2. 이번에는 하지 않았다 |

## 8. 한계

- 업무 문항은 Claude가 작성하고 검수했다. 사람 정답이 아니고, 사고 켬 99.5%는 문항이 추론하면 풀리게 깔끔하게 만들어졌다는 뜻이기도 하다.
- Jev 수치는 공개 결과를 가져다 썼다. 영어 벤치와 Decision Index의 표본 실행은 Jev와 행 수가 다르다. Decision Index는 벤치당 약 40요청이라 벤치별 수치는 오차가 크고, 영역과 지수 단위로 읽어야 한다.
- 지연은 이 서버 한 대에서, 다른 사용자가 없을 때 잰 값이다. Jev 지연은 측정자 환경의 네트워크를 포함한다.
- vLLM은 함께 계산되는 요청 구성에 따라 점수가 조금 달라진다. 같은 설정을 동시성만 바꿔 돌려도 정확도가 1%p 안팎 움직였다.
