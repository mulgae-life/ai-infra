# 보험 도메인 임베딩 파인튜닝 조사

> **목표:** 보험 용어·약관·상품 문서 검색에 맞춘 임베딩 모델을 만들기 위한 데이터 수집, 학습 데이터 구상, 파인튜닝 방법과 과정
> **조사 기준일:** 2026-10-07, 한국시간
> **작성 방식:** Claude(Claude Code)와 코덱스(Codex CLI)가 범위를 나눠 조사하고, 서로의 주장을 원문 사본으로 교차 검증한 뒤 Claude가 취합. 학습·추론·데이터 수집은 실행하지 않음.
> **원문 대조:** 수치·이용 조건은 원본 자료 폴더의 사본과 줄 단위로 대조. 미확인은 본문에 따로 표시.
> **선행 문서:** [korean-retrieval.md](korean-retrieval.md) — 한국어 검색 후보 모델과 라이선스
> **원본 자료:** [sources/2026-10-07_insurance-finetuning/](../sources/2026-10-07_insurance-finetuning/README.md)

## 1. 핵심 결론

- **파인튜닝보다 보험 검색 평가셋이 먼저.**
  - 이번 조사에서 권리와 평가 절차가 확인된 공개 한국어 보험 검색 평가셋을 찾지 못함. 기존 조사에서 확인한 보험 임베딩 비교도 단일 질문 후기 1건. [korean-retrieval.md 6절]
  - 평가셋 없이 학습하면 개선 여부를 판단할 수 없음.
- **공개 사례는 도메인 파인튜닝의 개선을 보고하지만, 보험 기대 개선폭은 미측정.**
  - 영어 금융 +3.56점(7B), 영어 의료 +5.22점(300M), 영어 보험 +8.6점(300M) 등 조건이 모두 다름. [S11, S19, S29]
  - 평가 질의를 학습 질의와 같은 방식으로 합성했거나, 시험 질의로 체크포인트를 고른 사례가 섞여 있음. 평균 내서 기대값으로 쓰지 않음.
- **보험 문서 특유의 위험은 "오답으로 잘못 표시된 정답(거짓 네거티브)".**
  - 표준약관의 같은 조항이 상품마다 다른 조 번호로 반복됨. 공개 표준약관 묶음에서 준거법 조항 9개의 첫 문장이 모두 같았고 조 번호는 제27조~제46조로 제각각. [S40]
  - 같은 문장을 네거티브로 학습하면 모델이 정답을 밀어내도록 배움. 동등 조항을 묶고 다중 정답을 보존하는 것이 필수. 모델 점수로 거르는 거짓 네거티브 필터는 발생률과 오류 유형을 측정한 뒤 비교.
- **학습 데이터는 "질의만 합성, 정답은 실제 원문".**
  - 사내 LLM(연구계 :5015 Qwen3.8-27B)으로 질의를 만들고, 정답은 실제 약관·문서 청크로 고정.
  - 정답 문서까지 합성하면 보장 조건·면책 조건을 지어낼 위험이 있음. [S05, S11]
- **첫 실험은 작게: 568M급 한국어 모델 + 1만 쌍 + 단순한 대조 손실.**
  - 기반 모델은 KURE-v1·Snowflake-ko·Qwen3-Embedding-0.6B 등을 보험 개발셋으로 비교해 고름. [S32, S33]
  - 손실은 `CachedMultipleNegativesRankingLoss`부터. 거짓 네거티브 필터와 일반 성능 보존 기법은 측정 결과를 보고 비교 실험으로 추가.
- **파인튜닝 없이 얻는 개선부터 기준선에 넣어야 공정.**
  - 청크 앞에 상품명·조 제목 같은 맥락을 붙이는 방법, BM25 결합, 리랭커. 문맥 검색 사례에서 세 가지를 차례로 더할 때 상위 20개 검색 실패율이 누적으로 35%, 49%, 67% 줄었음(5.7% → 3.7% → 2.9% → 1.9%). [S22]
  - 상품·시행일·접근 권한은 임베딩이 아니라 메타데이터 필터로 처리.
- **공개 보험 데이터의 상당수는 학습 이용 조건 확인이 필요.**
  - 바로 쓰기 쉬운 쪽: 우체국보험 약관 API(이용허락범위 제한 없음), AI Hub(학습 결과물 영리 이용 허용. 원 데이터는 학습용 한정이라 평가 이용 범위는 개별 약정 확인). [S36–S39]
  - 확인 필요: 금감원 분쟁사례(수익·상응 혜택 목적은 사전 허락), 손보협회 FAQ·용어, 법제처 표준약관. [S40–S43]
  - 제외: 영어 InsuranceQA(연구 목적 한정). [S46]
- **서빙 경로는 아직 없음.**
  - 현재 게이트웨이에 `/v1/embeddings`가 없음. 별도 임베딩 프로세스와 접속 경로가 필요. [`llm-serving/vllm/vllm_gateway.py`]
  - vLLM·TEI는 XLM-R·Qwen3 구조를 지원하지만, 개별 한국어 체크포인트의 동작과 운영계 메모리는 실측 전. [S26, S27]

  - 행마다 원천 문서 식별자, 권리 근거, 허용 용도, 확인일을 연결. 미확인 자료는 학습·검수·평가 파일에 넣지 않음.
  - "제외"는 이번 상용 활용 후보에서 뺀다는 뜻.
- 공개 보험 연구 데이터 두 건도 확인했으나 바로 쓸 수 없음.
  - 한국어 보험 분쟁 판단 데이터 473건(2024): 검색이 아닌 판단 분류 과제이고 데이터 배포·라이선스 미확인. [S13]
  - 한국어 암보험 대화 QA(2022): 수집 12,734건에서 2,295건 선별 + 수작업 892건. 공개 범위·상용 조건 미확인. [S14]
- `robots.txt`는 검색 봇 대상 제외 경로일 뿐 학습용 대량 수집 허가가 아님. 제공 API, 정식 다운로드, 기관 허가를 우선.

### 3.2 수집할 때 남길 기록

- 문서마다 `source_url`, `source_document_id`, `issuer`, `product_id`, `rider_id`, `effective_from`, `effective_to`, `document_family_id`, `article_id`, `content_hash`, `license_or_permission`, `accessed_at`.
- 보통약관과 특약, 구상품과 신상품, 다른 회사의 같은 제목 조항을 구분.
- 면책기간·감액기간·갱신·자기부담금 같은 숫자와 조건은 원문 그대로 유지.
- 판매가 끝난 약관도 과거 계약 질의에는 정답일 수 있음. 최신본으로 덮어쓰지 않음.

### 3.3 공개 평가 질의의 현실

- 권리가 확인된 **실제 사용자 질의**를 수백 개 단위로 확보할 공개 원천은 이번 조사에서 찾지 못함.
- 손보협회 FAQ와 금감원 분쟁 쟁점은 평가 유형을 설계할 씨앗. 다만 고객 질의 원문이 아니고 이용 조건 확인이 필요.
- 평가셋은 출처를 나눠 결과를 분리 보고: 실제 로그, 공개 쟁점을 바탕으로 전문가가 작성, 합성 후 사람 검수.

## 4. 학습 데이터 구상

### 4.1 쌍의 종류

| 유형 | 질의 | 정답 | 목적 | 주의 |
|---|---|---|---|---|
| A. 합성 질의–청크 (주력) | LLM이 만든 질문 | 실제 약관·상품요약서·내부 문서 청크 | 실제 검색 분포 학습 | 청크 단위·형식을 서빙과 동일하게 |
| B. 실제 질문–근거 | FAQ·상담·분쟁 쟁점의 질문 | 근거 조항 또는 승인 답변 | 실제 질의 분포 | 평가셋과 겹치지 않게. 개인정보 처리 |
| C. 용어–정의 | 보험 용어·약어 | 용어사전 정의 | 어휘 연결(실손, 납입면제, 해지환급금 등) | 같은 뜻의 정의를 네거티브로 쓰지 않음 |
| D. 구어–약관어 | "보험료 안 내도 되는 경우" | 납입면제 조항 | 고객 표현과 약관 문체의 간극 | 사람 검수 표본 필수. Google 안내서도 같은 의도의 바꿔 말하기를 정답, 같은 도메인의 다른 의도를 네거티브로 둔 삼중항을 예로 듦(의료보험 보장 ↔ 건강보험 혜택, 네거티브는 생명보험 해지) [S21] |
| E. 조 제목–본문 | "제3조(보험금의 지급사유)" | 해당 본문 | 값싼 약지도 | 표면 일치 지름길을 배울 위험 → 소량만 |

### 4.2 합성 질의 생성

- **정답 원문 고정, 질의만 생성.** 조건을 바꾼 대조 문항은 임의로 만들어 정답으로 확정하지 않고, 실제 반례 조항을 찾아 연결.
- **다양성 변수**
  - 질문자 역할: 고객, 설계사, 콜센터 상담원, 보상 담당, 언더라이터. Qwen3-Embedding은 문서마다 질문자 역할을 배정해 합성 질의의 다양성과 현실성을 높였음. [S06]
  - 질의 형태·길이·명확도: 키워드, 짧은 질문, 사고 경위 서술. E5-mistral은 길이·명확도·난이도를 변수로 무작위 지정. [S05]
- **품질 관리 순서**
  1. 층화 표본 300개를 사람이 검수해 근거 일치율 95%를 목표로 함. 미달하면 생성량을 늘리지 않고 파싱·지시문·규칙부터 수정.
     - 95%는 표본에서 관측한 일치율의 제안 문턱. 전체 품질 보장이 아님. 유형별 오류와 표본 수를 기록.
     - 면책·금액·기간·부정 조건 오류가 나오면 전체 통과 여부와 별개로 그 유형을 고쳐 재검수.
     - 개발·시험 질의는 생성 예시나 학습 쌍으로 쓰지 않음.
  2. 기반 모델 검색에서 원 청크를 못 찾는 질의는 **바로 버리지 않음.** 생성 오류인지, 학습으로 메워야 할 어려운 질의인지 분류.
     - Promptagator의 왕복 일관성 필터는 **합성 데이터로 먼저 학습한 검색기**로 거르는 방식. 미학습 기반 모델의 검색 실패만으로 폐기하면 학습에 필요한 유효한 어려운 질의까지 제거할 위험이 있음. [S03]
  3. 상위 후보 중 더 나은 정답이 있으면 정답을 바꾸거나 다중 정답으로 둠. Gecko는 LLM 순위로 정답을 다시 골랐고, 약 15%가 원래 문단이 아닌 다른 문단으로 바뀜. [S02]
  - 참고: InPars는 생성 확률 상위 일부만 남기는 필터로 지표를 크게 올림. [S04]

### 4.3 하드 네거티브와 거짓 네거티브

- **하드 네거티브의 가치**
  - BAM(금융): 하드 네거티브 없이 Recall@1 57.5%, 1개 61.8%, 3개 62.8%. 저자는 1개로 효과 대부분을 얻는다고 정리. [S12]
- **채굴 방식**
  - NV-Retriever의 채굴 방법 비교(Figure 1)에서는 정답 점수를 기준으로 거르는 방식(TopK-PercPos)이 최선. 정답 점수의 95%를 넘는 후보를 버리는 설정. [S01]
  - 같은 논문의 교사 모델 비교(Table 1)에서는 BM25로 채굴한 네거티브가 가장 낮았고 무작위 네거티브가 그다음. 7B급 교사 모델이 가장 좋았음. [S01]
  - 이 수치는 영어 공개 QA 데이터·특정 학생 모델 조건의 결과. 보험 최적값이 아님.
  - sentence-transformers `mine_hard_negatives`의 문서 권장 예제가 이 방식(`relative_margin=0.05`, `sampling_strategy="top"`, 네거티브 10개 이하)에 해당. API 기본값은 `relative_margin=None`, `num_negatives=3`. [S16]
- **보험 특유의 거짓 네거티브**
  - 공통 조항 반복: 상품이 달라도 질의의 의도와 적용 조건에서 동등한 조항은 추가 정답 후보. 상품·시기가 빠져 판정할 수 없으면 조건 부족으로 분류. [S40]
  - 숫자만 다른 조항(1종·2종, 갱신형·비갱신형): 질의가 그 차이를 지정할 때만 진짜 네거티브. 상품이 빠진 질의를 무조건 다중 정답으로 만들지도 않음(추가 질문이 필요한 질의일 수 있음).
  - 같은 내용은 **조 번호가 아니라 내용**으로 묶음. PDF 추출의 글자 순서 오류 때문에 공백만 지운 해시로는 부족할 수 있음.
- **거짓 네거티브를 다루는 기법 3가지 — 판정 기준과 단계가 다름**

| 기법 | 단계 | 판정 기준 | 출처 |
|---|---|---|---|
| TopK-PercPos | 채굴 | 정답 점수 × 0.95 초과 후보 제외(정답 점수가 양수일 때) | [S01, S16] |
| GISTEmbed | 학습 중 배치 | 별도 안내 모델 점수로 정답과 관련 있을 법한 배치 내 텍스트 제외 | [S09, S15] |
| Qwen3 마스크 | 학습 손실 | 정답 점수 + 0.1 초과 또는 정답과 같은 문서면 제외. 질의–질의, 문서–문서 항에도 적용 | [S06, S24] |

  - 정답 코사인이 0.8이면 첫째 경계는 0.76, 셋째는 0.9. 같은 후보를 다르게 처리하므로 서로 대체하는 설정이 아님.
- **측정부터:** 개발 질의 총 100개(유형별 층화)에서 이미 알려진 정답을 뺀 상위 후보를 최대 10개씩, 최대 1,000쌍을 사람이 판정.
  - 유효한 네거티브, 추가 정답, 판정 보류로 나눔.
  - 판정 가능한 후보 중 추가 정답 비율, 보류 비율, 추가 정답이 하나 이상 있는 질의 비율을 따로 냄. 상위 1·3·10 구간별로 분모와 함께.
  - 이 결과로 채굴 개수와 필터를 결정.
- **채굴 운영 규칙**
  - 첫 교사는 선택한 기반 모델의 **추가 학습 전 고정 체크포인트**.
  - 학습용 네거티브는 학습 분할에서만 채굴. 개발 질의·정답을 학습 네거티브로 가져오지 않음.
  - `relative_margin=0.05`는 시작값일 뿐 정답 판정을 대신하지 않음. 상품·조건이 다른 가까운 조항은 진짜 네거티브인지 확인한 뒤 사용.
  - BM25는 후보를 넓히는 용도로만. 검수 없이 네거티브로 확정하지 않음.

### 4.5 일반 데이터

- 목적: 보험 학습으로 일반 한국어 검색 성능이 떨어지는 것을 막음.
- 혼합 0%·20%와 학습 후 병합을 같은 개발셋에서 비교. 어느 쪽도 미리 우월하다고 보지 않음.
- AI Hub 71610 같은 금융·법률 독해를 일반 데이터로 쓰면 Snowflake-ko가 이미 학습한 분포와 겹침(카드에 "금융 법률 문서 기계독해" 명시). [S33]
- 그래서 일반 성능 검증 과제는 AI Hub에서 나오지 않은 것으로 고름(예: MIRACL, Ko-StrategyQA).
  - 알려진 중복을 줄이는 출발점일 뿐, 기반 모델이 비공개 자료로 미리 본 적이 없다고 보장하지 않음. 공개 학습 목록과 미확인 범위를 기록.
  - 일반 성능은 같은 고정 과제의 학습 전후 변화로 측정.
- 병합은 선택한 기반 모델과 그 기반에서 추가 학습한 모델 사이에만. 서로 다른 기반 후보끼리 섞지 않음.

### 4.6 청크와 맥락 헤더

- 학습 청크는 서빙 청크와 같은 단위로 자름.
- PDF 페이지와 청크를 연결해 표의 행·열, 단위, 부정어, 각주·준용 관계를 표본으로 확인. 필수 조건이 잘리거나 추출 중 훼손된 청크(예: 표준약관 사본의 음절 순서 뒤섞임)는 질의 생성 전에 다시 파싱하거나 제외. [S40]
- 길이는 모델별 토크나이저로 잼. 같은 원문·청크에서 모델별 근거 잘림 비율을 기록하고, 512·1024(필요하면 1300)를 비교.
- 보장 내용·보험금 표는 핵심 근거. 표를 마크다운으로 유지할지 행 단위 문장으로 풀지는 파싱 표본 단계에서 정함. Snowflake-ko 카드는 마크다운 표 검색에 맞췄다고 주장. [S33]
- 맥락 헤더(상품·특약·시행일·조 제목)는 E0 기준선(파인튜닝 없이 기성 모델을 비교하는 첫 실험, 7.1의 3단계)의 비교 축.
- 상품·시행일·접근 권한은 메타데이터 필터로 처리.
  - 헤더는 임베딩 입력의 맥락이고 권한 통제는 별도 필터. 헤더를 뺀 비교에서도 권한 필터는 유지.
  - 질의에서 상품·시행일이 불분명하면 필터값을 임의로 채우지 않고 조건 부족 질의로 처리.

## 5. 평가셋 설계

- **규모와 분리**
  - 개발 200개를 먼저 만들어 주석 기준을 다듬음. 모델·데이터·설정 선택은 개발셋에서만.
  - 시험셋은 확보량과 주석 비용에 맞춰 정함(목표 600개). 최종 구성을 확정한 뒤 한 번만 엶.
- **시험셋 유형 구성안 (600개 기준, 제안)**

| 유형 | 수 |
|---|---:|
| 용어·일반 보장 | 180 |
| 면책·부정·금액 조건 | 180 |
| 조문 참조·장문 | 120 |
| 상품·시행일 구별 | 60 |
| 답 없음·조건 부족 | 60 (검색 평균에서 분리, 추가 질문 필요 판단을 따로 평가) |

- **관련도 정의와 지표 (제안)**

| 관련도 | 뜻 |
|---|---|
| 2 | 직접적인 답변 근거, 또는 필수 근거 묶음의 구성원 |
| 1 | 배경·보조 관련 |
| 0 | 해당 질의·상품·시기에서 근거가 아님 |

  - nDCG 이득은 `2^관련도 − 1`. Recall의 정답은 관련도 2로 고정.
  - 본문·별표·준용 특약이 함께 필요한 질의는 필수 근거 묶음으로 주석하고, 묶음을 모두 찾았는지(완전 회수율)를 따로 측정.
  - 정답표에는 질의·문서 ID, 관련도 등급, 필수 근거 묶음 ID를 저장. 공개 예제는 평가기(`InformationRetrievalEvaluator`)에 정답 문서 ID 집합만 넘김. 등급 이득, 관련도 2 기준 Recall, 묶음 완전 회수율을 계산하는 경로를 따로 확인하고 작은 수작업 예제로 검증. [S19]
  - 답 없음·조건 부족 질의는 정답이 있는 질의의 nDCG·Recall 평균에서 분리. 답 없음은 검색 결과를 유효 근거로 잘못 통과시킨 비율, 조건 부족은 추가 질문 대상으로 판정한 비율로 보고하고, 정상 질의를 불필요하게 보류한 비율도 함께 측정. 임계값은 개발셋에서 정하고 시험셋에서는 고정. (현업 확정 전 제안)
- **주석**
  - 핵심 조건 질의는 2인 검토.
  - 다중 정답 필수. 보험 QA 사례에서도 시험 질문 2,000개 중 760개가 정답 2개 이상. [S29]
- **두 평가 과제와 분할 규칙**

| 과제 | 뜻 | 분할 규칙 |
|---|---|---|
| 같은 색인 문서의 새 질의 | 실제 운영 상황 | 문서 공유 허용. 질문과 그 바꿔 쓴 질문들은 같은 쪽에 |
| 새 문서 일반화 | 신상품 대응 | 상품·템플릿·개정 계열과 동등 조항군을 학습·개발·시험 간 분리. 시험 문서에서는 합성 질의를 만들지 않음 |

  - 두 결과를 합산하지 않음.
  - 같은 제목이라고 모두 동등 조항으로 묶지 않음. 상품·조건·내용을 확인해 판정.
- **판정 풀**
  - 검색은 실제 규모의 전체 후보군에서 수행. 풀은 사람이 판정할 대상을 정하는 용도일 뿐 후보 말뭉치를 줄이는 용도가 아님.
  - BM25, 기성 모델 여럿, 하이브리드의 상위 k를 합쳐 판정.
  - 판정하지 않은 문서를 순위에서 빼거나 평가 도구 기본값으로 오답 처리한 결과를 최종 수치로 쓰지 않음.
  - 최종 비교 시스템의 상위 10개에 미판정 문서가 남으면, 모델명·점수를 가린 채 추가 판정하고 같은 정답표로 전부 다시 계산.
  - 상위 10개 판정률과 풀 밖 정답을 놓쳤을 한계를 함께 보고.
- **말뭉치 규모:** 실제 색인 규모로. 보험 사례 작성자는 정답 후보 200개에서 기반 모델 정확도@1 92%, 3,308개 전체에서 64.2%를 관찰. 질의 조건까지 통제한 비교는 아님. [S29]
- **평가 조건 고정:** 검색 대상 문서 목록·버전, 메타데이터 필터, 사용자 권한 조건을 평가 기록에 남김.
- **시험셋 운용**
  - 최종 구성을 확정한 뒤 시험 평가를 시작. 위의 가린 추가 판정은 허용하되, 그 결과로 모델·프롬프트·설정을 다시 고르지 않음.
  - 중대한 정답 오류를 고치면 정답표 버전을 올리고 비교 대상 전부를 다시 계산.
  - 시험 결과를 보고 설정을 바꿨다면 후속 실험으로 표시하고 별도 독립 시험이 필요.
- **통계**
  - 기준 모델과 후보 모델에 같은 군집 표본을 짝지어 재표집하는 부트스트랩을 주 분석으로. 군집은 문서 계열·동등 조항군. 같은 조항에서 나온 질문들은 독립 표본이 아님.
  - 두 과제를 따로 계산하고, 질의 출처·오류 유형별 결과를 함께 보고.
  - 군집 수와 크기 편차를 공개. 전체 평균의 가중 방식은 시험 전에 고정.
- **사전 노출 기록:** 기성 모델의 공개 학습 자료(예: Snowflake-ko의 AI Hub 데이터)와 평가셋이 겹칠 가능성을 따로 기록.

### 6.2 손실과 배치

- **기본: `CachedMultipleNegativesRankingLoss`(CMNRL, 캐시 없는 원형은 MNRL).** (질의, 정답[, 네거티브]) 형식의 기본 추천 손실(InfoNCE, 배치 내 네거티브). [S15]
- **경사 누적으로는 배치 내 네거티브가 늘지 않음.** CMNRL은 GradCache로 큰 대조 배치를 작은 미니배치로 나눠 계산. [S10, S15]
  - Schmid 사례의 "전역 배치 512"는 경사 누적이라 질의당 배치 내 네거티브는 31개. [S28]
  - GradCache도 메모리 무제한은 아님. 임베딩·유사도 행렬과 실행 비용은 남음.
- `BatchSamplers.NO_DUPLICATES`는 문자열 중복만 막음. 동등 조항 계열은 한 배치에 넣지 않도록 배치 구성을 따로 함.
  - 적용 단위는 캐시 미니배치가 아니라 네거티브를 공유하는 전체 대조 배치.
  - 명시적 네거티브 열에 다른 질의의 정답이나 동등 조항이 섞이지 않았는지도 검사.
- GISTEmbed·Qwen3식 마스크는 4.3의 측정 결과를 보고, 온도·배치·후보를 맞춘 같은 조건에서 비교.
  - GISTEmbedLoss 기본 온도 0.01, CMNRL `scale=20`은 온도 0.05. 비교 시 맞춰야 함. [S15]
  - 온도·배치를 맞춰도 대조 항과 점수를 내는 모델이 다를 수 있음. 차이를 기록하고, 다 통제하지 않았다면 "마스크 하나의 효과"로 해석하지 않음.

### 6.4 일반 성능 보존

- **가중치 병합(LM-Cocktail):** 파인튜닝 모델과 기반 모델을 섞음. 저장소 예시는 0.5:0.5이고, 대상 과제 예시 5개로 가중치를 자동 계산하는 함수도 있음. 같은 구조·같은 초기 가중치에서 출발한 모델끼리만. 일반 성능 보존을 보장하지 않으므로 개발셋에서 검증. [S08]
- **체크포인트 병합(Qwen3):** 학습 중 저장한 여러 체크포인트를 구면 선형 보간(slerp)으로 병합. 병합을 뺀 모델이 "considerably worse". 기반 모델과 섞는 LM-Cocktail과는 다른 방식. [S06]
- 목표: 일반 한국어 검증 과제 평균 하락 1점 이내(제안값).

### 6.5 1차 범위 밖

- **도메인 적응 사전학습(MLM·TSDAE):** 대상 말뭉치 사전학습 뒤 큰 라벨 데이터로 지도학습을 다시 해야 해 비용이 큼. [S17] GPL 결과(대상 도메인 적응 전 제로샷(zero-shot) 기준 모델 대비 최대 +9.3점, TSDAE+GPL 평균 +7.7점, nDCG@10)는 2021년 DistilBERT 기반. [S07]
- **Matryoshka:** 벡터 저장량이 병목일 때. 원본 `BAAI/bge-m3`는 Matryoshka 학습 모델이 아니라 vLLM이 차원 변경 요청을 거절함. 차원 축소를 추가 학습한 파생 모델은 학습 결과와 서빙 설정(`is_matryoshka`)을 따로 검증해야 함. [S26]
- **리랭커 점수 증류:** FlagEmbedding `add_reranker_score.py` 같은 경로가 있음. 2차 선택지. [S23]
- **리랭커 도메인 학습:** 임베딩과 별도 축. Hugging Face 리랭커 블로그 저자는 도메인에 학습한 작은 리랭커가 더 큰 범용 리랭커를 이겼다고 보고(GooAQ 기준). 같은 `mine_hard_negatives`로 학습 데이터를 만듦. [S20]

## 7. 실험 과정

### 7.1 착수 순서 (첫 5단계)

기간은 실측 근거가 없어 적지 않음. 선후관계와 다음 단계로 넘어가는 조건만 정함. E0~E4는 실험 단계 번호로, E0은 파인튜닝 없는 기준선, E1부터 학습 실험.

| 순서 | 작업 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 1 | **쓸 수 있는 자료와 현업 검수 범위 확정.** 파일별 권리 상태, 상품·개정 계열, 제공 가능한 실제 질의, 검수 담당자, 기존 색인 규모 목록 | 승인 자료와 보류 자료가 분리됨. 접근 권한과 현업 판정 담당자가 정해짐 |
| 2 | **파싱 표본 검증과 분할·주석 규칙.** PDF 페이지–청크 연결, 표·단위·부정어·준용 관계, 동등 조항군 확인. 개발 200개 작성, 시험 후보의 계열과 질의는 따로 잠금 | 필수 조건이 잘리거나 추출 중 훼손된 청크는 질의 생성 전에 다시 파싱하거나 제외함. 관련도 0/1/2, 답 없음, 필수 근거 묶음, 두 과제 분할 규칙을 실제 표본에 적용할 수 있음 |
| 3 | **E0 기준선(개발셋).** 기성 모델 후보와 현재 검색기 비교 → 상위 후보에 맥락 헤더·BM25 결합 비교. 판정 풀 추가 판정과 거짓 네거티브 측정(4.3)을 함께 | 같은 후보군·모델별 형식·근거 잘림을 확인한 비교표. 첫 학습 후보 1개와 실제 오류 유형이 정해짐. 파인튜닝 없이 목표에 닿으면 파인튜닝 우선순위를 낮춤 |
| 4 | **1만 쌍 준비.** 합성 100문항으로 처리량 측정, 유형을 갖춘 300개 표본으로 품질 판정. 네거티브 1개 채굴 가능 여부. 같은 소량 데이터로 메모리·단계 시간 측정 | 품질 문턱과 핵심 조건 검수를 통과한 데이터 버전, 일반 데이터 혼합 가능 여부, 비용 추정, GPU 사용 계획 |
| 5 | **E1 1만 쌍 학습.** CMNRL + 배치 내 네거티브만, 학습률 1e-5·2e-5 | 같은 기반·최적 기성 구성 대비 개발 성능, 일반 성능 변화, 자원 사용 기록. 개선이 없으면 중단 규칙대로 원인 진단 |

### 7.2 이후 실험

- **E2 하드 네거티브:** 1개 → 3개. 4.3 측정에서 거짓 네거티브가 주된 오류면 GIST·마스크 비교.
- **E3 일반 성능:** 혼합 0%·20%, 병합 α 비교.
- **E4 확대:** 앞 단계가 합격하면 5만 쌍.
- **시험셋 평가:** 최종 구성으로 한 번(5절 시험셋 운용).
- **서빙 검증:** 학습 프레임워크와 서빙 출력 동등성, 부하·메모리, 재색인(8.2).
- 한 번에 설정 하나만 바꿈. 모든 선택은 개발셋에서. 한 단계가 끝났다고 시험셋 공개·확대·배포로 자동 진행하지 않음.

### 7.3 합격·중단 기준 (제안값)

| 판단 | 기준 |
|---|---|
| 파인튜닝 효과 | 같은 기반 모델 대비 nDCG@10 +3점(절대 차이 +0.03) 이상, 짝지은 군집 재표집 95% 신뢰구간 하한 > 0 |
| 정답 회수 | Recall@10 비하락. 면책·금액·날짜 등 핵심 조건 하위군에서 2%p 넘는 하락 금지. 표본 수·불확실성과 함께 보고 |
| 일반 성능 | 일반 한국어 검증 과제 평균 하락 1점 이내 |
| 답 없음 | 5절의 별도 지표(잘못 통과율, 추가 질문 판정률, 정상 질의 불필요 보류율)로 판정 |
| 도입 가치 | 가장 좋은 기성 구성(맥락 헤더·하이브리드·리랭커 포함) 대비로 따로 보고. 위 기준을 통과해도 품질·지연·메모리·재색인 비용을 보고 도입을 따로 결정 |
| 지연 | 동일 조건에서 질의 지연 95백분위가 기반의 1.2배 이내 |
| 중단 | 두 학습률의 1만 쌍 실험에서 개선이 없으면 규모를 늘리지 않음. 파싱·주석·누설·거짓 네거티브·필터를 다시 검토 |

### 7.4 비용 견적 방법

- 공개 사례의 학습 시간(예: 300M 모델 L40S 605초 [S29])은 PDF 처리·합성·채굴·검수·재색인을 포함하지 않음. 568M 한국어 모델의 견적도 아님.
- 소량 실측으로 산출.
  - 합성: 생성 시도 수가 아니라 검수 후 채택된 쌍 수로 처리량 계산.
  - 학습: 계획한 전체 단계 안에서 최대 100단계 측정. 준비·예열·인코딩·평가 시간을 구분.
  - 인력 검수와 재색인 비용은 따로 포함.
- 문서 수·길이·동시성 가정 없이 총비용을 확정하지 않음.
- GPU 3은 교사 채굴 → 교사 종료 → 학습 순으로 사용. 공유 생성 서버(:5015)의 동시 요청 상한을 정함.

## 8. 도구와 서빙

### 8.1 학습 도구

| 도구 | 용도 | 확인한 기능 |
|---|---|---|
| sentence-transformers [S15, S16, S18] | **1순위.** XLM-R 계열 학습 | `SentenceTransformerTrainer`, CMNRL·GIST·Matryoshka 손실, `mine_hard_negatives`, LoRA, `InformationRetrievalEvaluator` |
| FlagEmbedding [S23] | BGE-M3의 희소·다중 벡터 머리까지 학습할 때 | 데이터 형식 `{query, pos[], neg[], pos_scores, neg_scores, prompt}`, `hn_mine.py`, 리랭커 점수 추가, bge-m3 통합 학습 예시(학습률 1e-5, 온도 0.02) |
| ms-swift [S24] | Qwen3-Embedding 학습 | InfoNCE(온도 기본 0.1), `INFONCE_MASK_FAKE_NEGATIVE`(정답+0.1 초과 제외), 지시문은 `system` 메시지 |
| LM-Cocktail [S08] | 가중치 병합 | `mix_models`, `mix_models_with_data` |

### 8.2 서빙

- **구조 지원**
  - vLLM `--runner pooling` + `/v1/embeddings`: XLMRobertaModel(bge-m3, multilingual-e5 등), Qwen3(Qwen3-Embedding), Gemma3TextModel(embeddinggemma), ModernBertModel. ColBERT 계열은 별도 토큰 임베딩 경로. [S26]
  - TEI: XLM-RoBERTa(절대 위치), Qwen3, Gemma3, ModernBERT. 예시에 Snowflake-arctic-embed-l-v2.0, Qwen3-Embedding-0.6B. [S27]
- **확인 필요**
  - 한국어 파생 체크포인트(KURE-v1, Snowflake-ko, PIXIE)의 풀링·정규화·프롬프트가 서빙에서 학습 때와 같은 출력을 내는지. 한국어·표·장문 표본으로 유사도·순위를 비교. 허용 오차는 비교 결과를 보기 전에 정함.
  - 운영계 메모리: vLLM `gpu_memory_utilization`은 인스턴스별 비율이고 같은 GPU의 다른 인스턴스를 고려하지 않음. 두 비율의 합은 예산 출발점일 뿐 기동 성공을 보장하지 않음. [S26]
  - 긴 입력·동시 요청에서 임베딩 프로세스의 최고 메모리와, 같은 GPU에 있는 기존 LLM의 지연 변화를 함께 측정.
- **접속 경로**
  - 현재 게이트웨이 라우트는 `/health`, `/v1/models`, `/v1/chat/completions`, `/v1/audio/*`, `/v1/realtime`, `/server-status`. `/v1/embeddings`가 없음.
  - 연구 검증은 별도 내부 임베딩 경로를 기본으로.
  - 운영 연결(게이트웨이 라우트 추가 또는 직접 연결)은 실제 호출자·인증·접근 제어 요구를 확인하고, 검증된 구성안을 갖춘 뒤 운영 변경 단계에서 결정.
- **버전 관리:** 모델, 문서 스냅샷, 청킹 규칙, 프롬프트, 색인 설정을 한 배포 단위로. 모델을 바꾸면 전체 재색인. 이전 모델·인덱스 쌍으로 되돌릴 수 있게 유지.

## 11. 결정이 필요한 사항

기술 기본값(평가 방법, 데이터 처리 방식, 학습 초기 설정, 중단 규칙)은 이 문서로 정함. 아래 오른쪽 열만 담당자 결정이 필요.

| 구분 | 기술 기본값으로 정한 것 | 담당자가 결정할 것 |
|---|---|---|
| 평가 | 개발·시험 분리, 두 과제 구분, 다중 정답, 미판정 처리, 짝지은 군집 재표집 | **현업:** 보장·면책·숫자 조건의 정답 기준과 중요한 오류 유형. **대표님·현업:** 운영 도입 품질 문턱(+0.03 등은 그때까지 제안값) |
| 자료·권리 | 권리 상태 기록, 질의 출처 구분, 실제 원문을 정답으로 고정 | **자료 소유 부서·권리 담당자(필요하면 법무):** 실제 사용할 파일의 학습·평가 범위와 외부 제공자 조건. 공개 열람이나 카드 표기만으로 기술 담당자가 권리를 승인하지 않음 |
| 사내 자료 제공 | 개인정보를 줄인 자료 사용, 상품·시기·권한 기록, 로그와 전문가 작성 질의 분리 | **소유 부서·현업:** 제공할 문서·상담 로그의 범위와 데이터 처리 경로. 실제 로그가 없으면 전문가 질의로 진행한 사실을 그대로 표시 |
| 주석 인력 | 개발 200개, 합성 검수 300개, 거짓 네거티브 점검 100개 질의를 초기 계획값으로 | **대표님·현업:** 검수 담당자와 투입 가능량. 시험 600개 목표와 2인 검토 범위는 이 안에서 확정 |
| 모델·학습 | 후보 비교, 단순 손실부터, 초기 설정, 조건부 채굴·혼합·병합, 확대 중단 규칙 | 미니배치·길이 조정은 기술 담당. **운영 담당:** GPU 사용 시간·공유 서버 부하 한도. **대표님·예산 담당:** 추가 유료 자원 |
| 서빙·배포 | 별도 임베딩 프로세스로 검증, 모델·인덱스 공동 버전 관리 | **운영 담당:** 호출 경로·인증·서비스 수준·변경 시간대. **대표님·현업:** 최적 기성 구성 대비 이득과 비용을 보고 도입 여부 |

- 권리가 미확인인 자료는 그 자료만 보류. 승인된 자료로 주석 기준·파싱 표본·기준 실험은 진행 가능.
- 자료 사용이나 비용 지출이 필요한 단계는 기술 기본값 합의만으로 허가된 것으로 보지 않음.
