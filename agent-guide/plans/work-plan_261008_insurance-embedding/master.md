## 전체 그림

```
결정·사람  ┌ 결정 요청서 ┐   ┌ 표본 허용 ┐  ┌ 현업 인력 ┐   ┌ 추가 판정 ┐   ┌ 합성 검수 ┐
           │             │   │ 조건 대조 │  │ (주석)    │   │           │   │ 학습 허용 │
           │             │   │ 판정 백업 │  │           │   │           │   │           │
진행       P0 ──▶ P1 ─────────▶ P2 ──────────▶ P3 ──────────▶ P4 ──────────▶ P5 ──────────▶ P6
           준비   기반·평가기   실제 원문     초기 주석      E0 기준선      학습 준비       E1
                  (직접 쓴 예문) (파싱·청크)   (50 → 200)     (학습 필요?)   (총 1만 쌍)
공유 자원                                                    GPU 한도        :5015 한도      GPU 시간대
                                                                                            저장 예산
```

- 위 칸은 그 단계에서 **추가로 필요한 주요 조건**이다. 앞 단계의 조건이 사라지는 것은 아니다.
- 화살표는 산출물의 의존 관계다. 결정을 기다리는 동안 P1 준비나 자원 협의는 병행할 수 있다.
- P4 끝에 갈림길이 있다. 기성 구성으로 현업이 중요하게 보는 오류가 해결되면 P5·P6을 생략하고 그 근거를 보고한다.

| 단계 | 하는 일 | 넘어가는 조건 | Part |
|------|---------|---------------|------|
| P0 준비 | 결정 요청서 작성·전달 | 5건 각각에 담당과 필요 시점이 붙음. 전달 자체를 실행 허가로 보지 않음 | part1 |
| P1 기반·평가기 | 학습 환경, 원천 목록, 권리 게이트, 평가기. 직접 쓴 예문으로 검증 | 게이트가 미정 자료를 막음. 평가기가 손계산과 일치 | part1 |
| P2 실제 원문 | 허용된 표본을 파싱하고 청크로 자름. 동등 조항 묶기 | 훼손률과 제외 범위를 기록함. 핵심 조건이 훼손된 청크는 다음 단계로 넘기지 않음 | part2 |
| P3 초기 주석 | 분할, 시험 계열 봉인, 50개 시범 → 개발 200개 초기 정답 | 주석 기준 확정. 200개를 못 채우면 축소 범위와 예비 결과임을 명시 | part2 |
| P4 E0 | 후보 검색 → 추가 판정 → 비교표·오류 분류. 거짓 네거티브 진단 | 학습 후보 1개, 또는 "학습 불필요" 근거, 또는 판단 보류 사유 | part2 |
| P5 학습 준비 | 합성 처리량, 300개 표본 검수, 총 1만 쌍 조립 | 표본 품질 문턱 통과, 핵심 조건 오류 수정, 학습셋 이력 기록 | part3 |
| P6 E1 | 두 학습률 비교, 일반 성능 전후 비교 | 7.3절 기준으로 "후속 검증 가치 있음" 또는 "원인 진단" | part3 |

## 결정 요청 (P0 산출물의 뼈대)

대표님이 고르기만 하면 되게 쓴다. 담당자가 결정하고, 우선순위 충돌·추가 비용·새 저장 위치처럼 대표님 판단이 필요한 것만 올린다.

| # | 결정 | 묻는 것 | 담당 | 필요 시점 | 없을 때 진행 범위 |
|---|------|---------|------|-----------|-------------------|
| 1 | 첫 자료 범위 | 소량 표본 파일 목록과 파일별 허용 용도(개발·평가·학습). 우체국 API를 쓴다면 공공데이터포털 활용신청 주체와 상품명 목록 확보 방법. 일반 평가 과제와 기성 모델의 이용 조건 확인 결과(기술 담당이 근거 정리) | 자료 소유자·권리 담당자 | 개발 표본 P2 전, 평가 용도 P3 전, 학습·일반 평가 P5 전 | 허용된 용도의 앞 단계까지 |
| 2 | 현업 인력 | 실제 표본의 핵심 조건 대조 담당, 50개 시범 담당, 개발 200개 확대 여부, 핵심 조건 2인 검토자, 질의 작성 방식(현업 직접 / LLM 초안 후 수정), E0 추가 판정과 합성 300개 검수 투입량 | 대표님·현업 | 조건 대조 P2 검수 전, 주석 P3 전, 추가 판정 P4, 합성 검수 P5 | 원문 추출 준비까지. 의미 검수를 통과했다고 표시하지 않음 |
| 3 | 공유 자원 | E0 동시 사용 한도, :5015 합성 요청 한도, E1 시간대, 모델·체크포인트·캐시의 저장 예산 | 운영 담당 (충돌·비용은 대표님) | E0 한도 P4 전, 합성 한도 P5 전, 시간대·저장 예산 P6 전 | 해당 단계 앞까지 |
| 4 | 사람 판정 백업 | `data/labels/`의 백업 위치, 책임자, 복구 확인 방법 | 운영·자료 담당 제안 → 대표님 | 사람 검수 기록이 처음 생기기 전(P2 검수) | 사람 검수·판정을 시작하지 않음 |
| 5 | 소비자 확인 | hw-chatbot이 소비자 후보인지, 지금 쓰는 보험 검색기가 있는지(있으면 E0 비교에 넣음) 사실 확인 | 대표님 | 초기 | 영향 없음. 연구는 진행 |

- 반복해서 묻지 않을 것: 라이브러리 최신화 여부, 평가 지표, 청크 버전 관리, AI 검토를 사람 수에 넣지 않는 원칙. 근거를 갖춘 기술 기본안으로 둔다.
- 원천 목록에 적었다고 사용 허용이 생기지 않는다. 허용이 이미 확인된 항목은 다시 묻지 않는다.

| 항목 | 사실 | 계획에 주는 의미 |

| GPU 2 | 약 40GB 사용. 컨테이너 밖 프로세스라 정체 미확인 | 사용 후보로 잡지 않음 |
| GPU 3 | 약 21GB 사용, 사용률 100%. hw-chatbot 임베딩 서버(:8020)와 CFD 계산 작업이 같이 돎 | E0·E1 모두 착수 직전 재실측과 사용 한도 합의가 필요 |
| 기록 불일치 | hw-chatbot 문서의 같은 날 기록("임베딩 서버 안 떠 있음, 여유 약 14GB")과 실측이 다름 | 문서가 아니라 착수 직전 실측을 기준으로 함 |

| 평가 도구 | 표준 평가기(`InformationRetrievalEvaluator`)는 정답을 맞음·틀림으로만 받고 정답 없는 질의는 뺌 | 관련도 0/1/2, 필수 근거 묶음, 답 없음 지표는 직접 만든 평가기가 필요 |
| 자료 | 우체국보험 약관 API는 인증키와 상품명이 필수. 공개 명세에 전체 상품 나열 방법이 없고, 전체 조회 가능 여부는 미확인. "이용허락범위 제한 없음"은 API 표기이고 연결 PDF의 권리까지 확정하지 않음 | 키 발급과 파일 권리 확인은 별개 관문 |
| 디스크 | `/workspace`·`/models`가 같은 디스크, 여유 114GB | 저장 예산이 필요 |
| 로컬 모델 | `Qwen3-Embedding-0.6B`만 있음 | E0 후보는 내려받기와 이용 조건 기록이 필요 |

라이브러리와 평가 도구 행은 코덱스가 원문 사본(PyPI 메타데이터, 배포본 소스)으로 확인했고, Claude가 같은 사본으로 다시 대조했다.

## 처음부터 지킬 것

- **평가**: 관련도 0/1/2와 이득 `2^관련도 − 1`, 다중 정답, 필수 근거 묶음을 쓴다. 두 평가 과제(같은 문서의 새 질의 / 새 문서)와 질의 출처를 나눠 보고한다
- **검색 대상과 판정 풀**: 검색은 승인된 연구 범위의 전체 후보 말뭉치(목록·버전·규모 고정)와 상품·시행일·권한 필터 조건에서 한다. 판정 풀은 사람이 판정할 대상을 고르는 용도이고 후보 말뭉치를 줄이지 않는다. 미판정 문서를 오답으로 처리한 결과를 최종 수치로 쓰지 않는다. 비교 대상 상위 10개에 남은 미판정 문서는 모델명을 가리고 추가 판정한 뒤 공통 정답표로 다시 계산한다
- **분할**: 같은 문서의 새 질의 과제는 문서 공유를 허용하고 질의와 그 바꿔 쓴 질의를 한쪽에 둔다. 새 문서 과제는 상품·개정 계열과 동등 조항군까지 학습·개발·시험 사이에서 나누고, 시험 문서로는 합성 질의를 만들지 않는다
- **누설**: 시험 계열은 학습 자료로 쓰기 전에 먼저 분리·봉인한다. 시험셋은 `--final`로만 열고, 열 때마다 기록한다
- **동등 조항**: 같은 조항이 상품마다 다른 번호로 반복된다. 내용으로 묶고, 정답과 오답이 같은 묶음에서 나오지 않게 관리한다
- **사람과 AI 구분**: 코덱스 검토는 사람 검수 수와 2인 검토에 넣지 않는다. LLM이 초안을 쓴 질의는 현업이 고쳐도 출처를 따로 기록한다
- **사람 판정 백업**: 사람 검수·판정을 시작하기 전(P2 검수부터)에 백업 위치를 정한다
- **환경**: 학습과 서빙은 다른 환경에 둔다. 비교하는 동안 모델·라이브러리·문서·청크 규칙의 버전을 고정하고, 바뀌면 영향받은 기준선을 다시 잰다
- **공유 자원**: 착수 직전 GPU·디스크를 다시 잰다. 다른 작업을 임의로 멈추지 않는다
- **결론 표현**: 같은 기반 대비 개선과 최적 기성 구성 대비 가치를 따로 보고한다. 개발셋 결과를 독립 시험 합격이나 도입 승인으로 넓히지 않는다

## 전체 검증 계획

- [ ] **평가기**: 직접 쓴 예문으로 등급 nDCG, 관련도 2 기준 Recall, 묶음 완전 회수율, 답 없음·조건 부족 지표를 손계산과 대조
- [ ] **권리 게이트**: 미정·제외 자료와 허용되지 않은 용도의 요청이 거부되는지 시험
- [ ] **원문 품질**: 파싱 표본을 원문 화면과 대조해 핵심 조건 훼손률과 제외 범위를 기록
- [ ] **누설**: 같은 문서 과제는 같은 질의군이 학습·개발·시험에 걸쳐 있지 않은지, 새 문서 과제는 같은 계열·동등 조항군이 걸쳐 있지 않은지 검사
- [ ] **재현**: 학습셋 한 행에서 원본 파일과 권리 근거까지 거슬러 올라가는지 확인
- [ ] **판정**: E0와 E1을 같은 공통 정답표·같은 평가 조건으로 계산했는지 확인
